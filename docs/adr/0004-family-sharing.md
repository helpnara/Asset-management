# ADR-0004 · 배우자 공유는 CloudKit shared database로, v1 이후

**상태**: 보류 (v1.1 후보) · 2026-09 — **2026-09-06 후속 참고**

> 실기기 사용 후 배우자·자녀 공유 요청이 들어왔다. 이 문서가 착수 조건으로
> 적어 둔 "배우자에게 무엇을 고치고 싶은지 확인" 의 답이 나온 셈이다:
> **전체 편집 · 변경 이력 관리.** 진행 계획과 발견한 문제는
> [docs/08-feedback.md](../08-feedback.md) 의 13번에 있다.
>
> **이 문서가 약속한 준비(레코드 간 참조를 UUID 로도 병행 보관)가 실제로는
> 안 돼 있다.** `Account.owner` 와 `Holding.account` 가 관계뿐이다.
> 2차 작업에서 `ownerID` · `accountID` 를 넣기로 했다.

## 맥락

앱 이름 그대로 "우리 가족" 현황판이므로 배우자도 보고 싶어 할 가능성이 큽니다.
그러나 배우자는 별도의 Apple 계정을 씁니다. CloudKit **private** database는
같은 Apple 계정의 기기 사이에서만 동기화됩니다.

## 결정

**v1에서는 하지 않습니다.** 한 명이 입력하고, 공유는
[1페이지 PDF 내보내기](../02-screens.md#263-1페이지-내보내기)로 대신합니다.

v1.1에서 다루되, 방식은 **CloudKit shared database (`CKShare`)** 로 갑니다.
자체 서버나 계정 시스템은 여전히 도입하지 않습니다.

## 왜 v1이 아닌가

1. **데이터 모델이 바뀝니다.** 공유하려면 레코드를 커스텀 존(custom zone)에 넣어야 하고,
   `CKShare`의 루트 레코드를 정해야 합니다. SwiftData의 shared DB 지원은 private DB보다
   거칩니다. v1 스키마가 안정되기 전에 손대면 두 번 일합니다.
2. **권한 모델을 정해야 합니다.** 배우자는 읽기만? 자기 계좌만 편집? 전체 편집?
   이 결정은 실제로 써 보기 전에 내리면 틀립니다.
3. **충돌 처리가 실제 문제가 됩니다.** 지금은 last-writer-wins로 충분하지만
   두 사람이 동시에 편집하면 그렇지 않습니다.
4. **v1 완료를 늦춥니다.** 이 앱은 먼저 한 사람에게 매일 쓸 만해야 합니다.

## 대안

| 대안 | 평가 |
|---|---|
| 자체 서버 + 계정 | 프라이버시 모델이 깨짐. Non-goal |
| iCloud Family Sharing 그룹 공유 | CloudKit private DB는 가족 공유로 자동 확장되지 않음. `CKShare`가 여전히 필요 |
| 읽기 전용 스냅샷 공유 (PDF·이미지) | **v1의 답.** 구현 비용이 낮고 실제 요구의 대부분을 충족 |
| 내보낸 파일을 iCloud Drive 공유 폴더에 두기 | 수동이지만 가능. v1에서 문서로 안내 |

## 결과

- v1 스키마 설계 시 **나중에 커스텀 존으로 옮길 수 있도록** 레코드 간 참조를
  `UUID` 값으로도 병행 보관합니다(관계에만 의존하지 않음).
- v1.1 착수 전에 실제 사용자(배우자)에게 "무엇을 보고 싶고 무엇을 고치고 싶은지"를 확인합니다.
