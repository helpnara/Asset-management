## 막힌 곳 — SwiftData 는 공유를 못 한다 (확인 완료)

CI 의 macOS 러너에서 SDK 에 직접 물었다 (`Tools/probe-swiftdata-sharing.sh`).
**컴파일러를 심판으로 썼다.**

```swift
public struct CloudKitDatabase {
  public static var automatic: CloudKitDatabase
  public static var none: CloudKitDatabase
  public static func `private`(_ privateDBName: String) -> CloudKitDatabase
}
```

`.shared` 가 없다. `CKShare` · `sharedCloudDatabase` · `func share` 가
SwiftData 인터페이스 전체에 **한 줄도 없다.** SwiftData 는 private
데이터베이스만 연다.

## 길 셋과 **실측한 비용**

빌드 22 기준으로 코드를 세었다. 감이 아니다.

```
App 코드          11,467줄
Core 코드          2,578줄   ← 순수 Swift. 어느 길로 가도 안 바뀐다
@Model                15개
@Query                82곳   ← 경로 B 에서 전부 손대야 하는 자리
import SwiftData      38개 파일
ModelContext 사용     36곳
Core 가 SwiftData 를 아는가   0곳   ← ADR-0002 가 값한 자리
```

| | 무엇 | 실제로 손대는 것 | 위험 |
|---|---|---|---|
| **A. raw CloudKit 공유 계층을 따로** | SwiftData 는 그대로, 공유용 커스텀 존에 손으로 미러링 | 새 동기화 계층 하나 + 충돌 해소 | **진실의 원천이 둘.** 이 앱이 가장 경계하는 "기록이 조용히 사라지는 것"을 정확히 만든다 |
| **B. Core Data 로 옮긴다** | `NSPersistentCloudKitContainer` 로 저장 계층 교체 | `@Query` **82곳** · `@Model` 15개 · 38개 파일 | ADR-0001 뒤집기. 다만 **CloudKit 쪽은 안 바뀐다** — 이미 `CD_` 형식이다 |
| **C. 공유를 안 한다** | 1페이지 PDF·JSON 으로 대신 | 없음 | 요청("아내가 직접 쓴다")을 못 채운다 |

### 권고 — **B**, 다만 한 번에 다 옮기지 않는다

**클라우드 쪽은 이미 Core Data 형식이다.** 3차에서 올린 스키마가 `CD_Member`,
`CD_entityName` 인 것이 그 증거다. SwiftData 가 속으로 Core Data 를 쓰기
때문이고, 그래서 **저장된 데이터는 그대로 두고 접근 계층만 바꾸는** 일이 된다.
A 처럼 미러링 계층을 새로 만드는 것보다 실패 지점이 적다.

`Core` 2,578줄은 손댈 것이 하나도 없다 — SwiftData 를 아예 모른다.
ADR-0002 를 지켜 온 값을 여기서 받는다.

**옮기는 순서** (각 단계 끝에 쓸 수 있는 빌드가 나오게):

0. **보기 전용 상태** 먼저 — ✅ 빌드 23 에서 함(08-feedback 48번). 아래 참고.
   순서를 앞으로 당긴 이유는 **저장 계층과 아무 상관이 없어서**다. 1단계는
   화면이 하나도 안 바뀌는 빌드가 몇 주 나오는 일이라 그동안 테스트할 것이
   없는데, 이걸 먼저 해 두면 이전하는 내내 아내분 화면을 실제로 써 보면서
   개선점을 받을 수 있다
1. `NSPersistentCloudKitContainer` 로 컨테이너만 교체하고 **기존 화면은 그대로**
   — `@Query` 는 `@FetchRequest` 로, `@Model` 은 `NSManagedObject` 로.
   여기까지가 82곳의 대부분이다. **동작은 하나도 안 바뀐다**
2. 기기 두 대로 **되돌리기·백업**부터 확인한다 (40번이 여기서 값한다)
3. `share(_:to:)` 로 공유 붙이기 — 구성원 단위 권한은 `CKShare` 한 장에
   하나뿐이므로, **공유 하나 = 가족 하나**로 두고 앱 안에서 역할을 판정한다
4. 3단계에서 `\.canEdit` 에 **참가자 상태를 꽂는다.** 화면은 안 고친다 —
   0단계가 이미 그 값 하나만 읽게 해 두었다. 더보기의 미리보기 구역과
   `FamilyRole.swift` 는 그때 지운다

## 4차의 절반은 공유가 아니라 이것이다

지금 화면은 전부 **"고칠 수 있는 사람"** 을 전제로 만들어져 있다.
편집·삭제·추가 버튼이 곳곳에 있고, 주간 점검은 값을 적어 넣는 화면 자체다.
읽기 전용인 사람이 열었을 때 **눌러도 안 되는 버튼이 널린 화면**이 되면 안 된다.

미리 세어 둔다 (빌드 22 기준):

- `DeleteButton` · `confirmsDelete` — 삭제 자리
- `+` 추가 버튼 — 구성원 · 계좌 · 종목 · 목돈 · 연금 · 할 일 · 마일스톤 · 원칙
- 주간 점검 전체 화면
- 계획 탭의 모든 입력
- **백업 되돌리기** — 관리자만이어야 한다 (40번)

권한 상태를 환경값 하나(`\.canEdit`)로 내리고, 위 자리들이 그것을 읽게 하는
것이 가장 적은 변경이다. 3-1차에서 화면을 손볼 때 이걸 염두에 두었다.

**✅ 빌드 23 에서 했다** (08-feedback 48번). 환경값은 결국 둘이 됐다 —
`canEdit`(자기 것)과 `canManageHousehold`(가구 전체). 하나로 두면 아내분이
자기 계좌를 고칠 수 있게 넓히는 순간 계획 가정과 백업 되돌리기까지 함께
열린다. 지금은 더보기의 토글이 이 값을 정하고, 3단계에서 `CKShare` 참가자
상태로 바꿔 꽂는다.

**본인 것만** 으로 좁히는 것은 아직이다 — 어느 구성원이 그 참가자인지는
공유가 붙어야 알 수 있다. `editor` 는 지금 "구성원 단위 잠금은 없고 가구
설정만 잠긴 상태" 로 동작한다.

```
@Model            15개    (관계는 셋뿐 — 구성원→계좌, 계좌→종목, 스냅샷→줄)

Core              2,578줄  ← 한 줄도 안 바뀐다
```

`Persistence/` 1,729줄의 대부분은 `@Model` 에 붙은 **계산 로직**이다
(`Plan.projectionInput`, `Account.holdingSlices` …). 이건 `NSManagedObject`

## 착수 전에 걸린 것 셋

### 1. **Xcode 가 없으니 `.xcdatamodeld` 를 그릴 수 없다**

Core Data 모델은 보통 Xcode 의 모델 편집기로 만든다. 사용자도 나도 맥이 없다.

길은 둘이다.

| | 무엇 | 검증 |
|---|---|---|
| **A. `.xcdatamodeld` XML 을 손으로 쓴다** | `SlowRich.xcdatamodeld/SlowRich.xcdatamodel/contents` 는 그냥 XML 이다. 엔티티·속성·관계가 평평하게 나열된다 | **CI 가 컴파일한다.** 어긋나면 빌드가 깨진다 |
| B. `NSManagedObjectModel` 을 코드로 짓는다 | 파일 형식이 아예 없다 | 빌드는 통과하고 **런타임에** 터진다 |

**A 를 택한다.** 이 저장소는 컴파일러를 심판으로 쓰는 곳이고, B 는 심판을
런타임으로 미룬다.

다만 손으로 쓰지 않는다 — **`Tools/cloudkit/generate-ckdb.py` 와 같은 자리에서
만들어 낸다.** 그 스크립트는 이미 모델을 읽어 CloudKit 스키마를 뽑고 있다.
같은 입력에서 `.xcdatamodeld` 도 뽑으면 **둘이 어긋날 수 없다.** 지금
CI 가 모델과 `.ckdb` 를 대조해 빌드를 막는 그 장치를 그대로 쓴다.

### 2. **저장소 파일이 같은 것이어야 한다** ⚠️ 제일 위험한 곳

지금 `ModelConfiguration` 은 경로를 안 준다. SwiftData 의 기본은
`Application Support/default.store` 다.

`NSPersistentCloudKitContainer` 가 **다른 경로**를 열면, 앱은 멀쩡히 뜨는데
**빈 화면**이 나온다. iCloud 에서 다시 내려받긴 하지만 그 사이 몇 분 동안
사용자는 "몇 달치 기록이 날아갔다" 를 본다.

그래서 1단계에서 지켜야 할 것:

 · `NSPersistentStoreDescription.url` 을 **SwiftData 가 쓰던 그 경로**로 못박는다
 · 엔티티 이름은 클래스 이름 그대로, 속성 이름도 그대로 — SwiftData 가
   그렇게 저장해 두었다 (`.ckdb` 의 `CD_` 이름들이 그 증거다)

**되돌아갈 길이 있다.** 40번의 백업·되돌리기다. 옮긴 첫 빌드를 깔기 전에
`더보기 → 1페이지 · 백업 내보내기 → 전체 백업 만들기` 를 한 번 받아
파일 앱에 두시면, 최악의 경우에도 되돌릴 수 있다.
**이건 40번이 미리 값한 자리다.**

### 3. `@preconcurrency` 는 여전히 안 쓴다

`NSManagedObject` 도 `Sendable` 이 아니다. `@Model` 을 async 경계 너머로
안 넘긴 규칙(CLAUDE.md)이 **그대로 유효하다.** 바뀌는 것이 없다.

`@Model` 을 읽어 `App/SlowRich.xcdatamodeld` 를 뽑는다. 엔티티 15개 · 칸 145개.

### 심판을 셋 세웠다

| 무엇 | 무엇을 잡나 |
|---|---|
| `git diff --quiet App/SlowRich.xcdatamodeld` | `@Model` 을 고치고 모델 파일을 안 뽑은 것 |

마지막 것이 특히 중요하다. 리소스로 잡히면 빌드는 통과하는데 XML 이 그대로
번들에 복사될 뿐 아무도 안 읽는다 — **1a 가 하려던 일이 통째로 헛것이 된다.**

`Member: 모델에 없는 칸 — employerMatchMinor`, 엔티티 하나를 지우면
`CloudKit 스키마에만 있는 엔티티: Principle` 로 종료코드 1 이 난다.
늘 통과하는 검사는 검사가 아니다.

### 못 하는 검증도 적어 둔다

`ck.mjs export development` 로 **지금 iCloud 에 올라가 있는 스키마**를 읽을 수
있지만, 그 Development 스키마는 **우리가 `apply` 로 밀어 넣은 것**이라

그래서 1b 의 진짜 심판은 **CI 스크린샷 20여 장**이다. 화면이 하나라도 달라
보이면 옮기다 흘린 것이 있다. 그리고 **되돌아갈 길은 40번의 백업·되돌리기**다.


## 탐침이 답했다 — **판본 해시가 전부 달랐다**

1a 를 끝내고 1b(82곳 고치기)에 들어가기 전에 SDK 에 물었다. 답:

```
저장소(SwiftData): 15개 · 우리 모델: 15개
해시가 같은 엔티티: 0개
해시가 다른 엔티티 15개: (전부)
```

**엔티티 이름은 완벽히 맞는데 해시는 하나도 안 맞았다.** 하나둘이 아니라
전부라는 것이 단서였다 — 엔티티마다 따로 틀린 것이 아니라 **모든 속성에
걸리는 규칙 하나**가 틀렸다는 뜻이다.

### 내가 틀린 곳

생성기가 145개 속성을 **전부 옵셔널**로 뽑고 있었다. 근거로 적어 둔 것은
"CloudKit 은 필수 필드를 못 만든다" 였는데, ADR-0001 을 다시 보니 이렇게
적혀 있다:

| 모든 속성에 기본값 **또는** 옵셔널 필요 | 모든 `@Model` 속성에 기본값을 명시 |

**이 앱은 기본값 쪽을 골랐다.** 그러니 속성은 옵셔널이 아니고, Swift 가 `?` 를
붙인 열넷만 옵셔널이다. 옵셔널 여부는 판본 해시에 들어가므로 145개가 전부
어긋났다.

고쳤다 — 옵셔널은 Swift 선언 그대로, 기본값은 리터럴인 것만 적는다
(기본값은 해시에 안 들어가지만 CloudKit 이 본다).

### 못 믿는 결과 하나

경량 마이그레이션 쪽은 이렇게 죽었다:

```
Cannot migrate store in-place: attempt to write a readonly database
```

**모델이 안 맞아서가 아니라 파일이 안 열려서**다. 사본을 뜨도록 고쳤는데도
같은 자리에서 죽는 것을 보면 WAL 이 남은 사본이 온전하지 않은 듯하다.
아직 답이 아니므로 **답으로 세지 않는다.**

### 다음 한 바퀴에 여러 가정을 함께 묻는다

CI 한 바퀴가 10분이라 가정 하나씩 고쳐 넣으면 하루가 간다. 그래서 탐침이
모델을 불러다 **옵셔널 값만 바꿔 가며** 해시를 다시 세고, 규칙별로 몇 개가
맞는지 함께 찍는다.

 · 있는 그대로 (Swift 선언을 따름)
 · 속성을 전부 옵셔널로 ← 지금까지 하던 것
 · 속성을 전부 필수로

`15/15` 가 나오는 줄이 정답이다. 셋 다 아니면 옵셔널이 아니라 **타입 쪽**이
문제라는 뜻이고(UUID 를 어떻게 저장하는지 등), 그때는 경로를 다시 본다.

### 옵셔널을 뗐더니 `momc` 가 막았다

```
error: Account.id must have a default value [8]
```

44개가 걸렸다. CloudKit 미러링의 규칙이 여기서 다시 나온다 —
**옵셔널이거나 기본값이 있어야 한다.** 옵셔널을 뗐으니 이제 기본값이 필요하다.

Swift 쪽 기본값이 리터럴이면 그대로 쓰고(`1990` · `""` · `false`),
`UUID()` · `Date.now` · 열거형 rawValue 처럼 여기서 계산할 수 없는 것은
**자리만 채운다.** 실제 값은 언제나 이니셜라이저가 넣으므로 이 자리 값이
쓰일 일이 없고, 판본 해시에도 안 들어간다. 날짜는 `defaultValueString` 이
아니라 `defaultDateTimeInterval` 을 쓴다.

**이 검사를 로컬로 내렸다.** `momc` 가 CI 에서 처음 알려 주면 한 바퀴가
10분이다. `check-model-matches-ckdb.py` 가 이제 CloudKit 규칙까지 본다 —
필수인데 기본값 없는 속성, 옵셔널 아닌 관계, 역관계 없는 관계. 이것도
일부러 기본값 하나를 지워서 걸리는지 확인했다.

### 이래도 안 맞으면 — 준비해 둔 다른 길

우리가 지금 하는 일은 SwiftData 가 속으로 만드는 Core Data 모델을 **바깥에서
맞춰 보는 것**이고, 그 대응 관계는 애플이 문서로 약속한 적이 없다. 맞춘다 해도
다음 iOS 에서 달라질 수 있다.

그래서 안 맞으면 **저장소를 그대로 열려고 하지 않는다.** 대신 40번의
백업·되돌리기를 쓴다: 첫 실행에 SwiftData 에서 JSON 으로 뽑아 → 새 Core Data
저장소로 넣고 → 갈아탄다. 형식은 **우리가 만든 것**이라 애플의 내부 사정에
기대지 않는다. 대신 CloudKit 쪽에 이미 올라간 레코드와 어떻게 만날지를
따로 풀어야 한다.


## 답이 나왔다 — **15/15 일치. 1b 로 간다**

옵셔널을 Swift 선언 그대로 고치고 기본값을 채우자:

```
── 엔티티 판본 해시 대조 ──
  저장소(SwiftData): 15개 · 우리 모델: 15개
  해시가 같은 엔티티: 15개
  해시가 다른 엔티티: 없음
```

**우리가 `@Model` 에서 뽑은 Core Data 모델은 SwiftData 가 만든 저장소와
정확히 같다.** 마이그레이션 없이 그대로 열 수 있다는 뜻이다.

### 이 한 바퀴가 아낀 것

82곳을 다 고친 **뒤에** 이걸 발견했다면, 원인이 82곳 어딘가인지 모델인지
가려내는 데만 며칠이 걸렸을 것이다. 그리고 그 사이 사용자는 빈 화면을 봤을
것이다. 탐침은 세 바퀴(10분씩) 만에 답을 냈다.

틀린 것도 탐침이 짚었다. 내가 적어 둔 근거는 "CloudKit 은 필수 필드를 못
만든다" 였는데, ADR-0001 은 **"기본값 또는 옵셔널"** 이라고 적혀 있었다.
이 앱은 기본값 쪽을 골랐으므로 속성은 옵셔널이 아니다.

### 남은 것 — 1b 에서 여전히 조심할 곳

판본이 같다는 것은 **모델이 저장소를 열 수 있다**는 뜻이지, 1b 가 쉽다는
뜻은 아니다. 아직 이것들이 남아 있다.

| | 무엇 | 왜 |
|---|---|---|
| 저장소 경로 | `NSPersistentStoreDescription.url` 을 SwiftData 가 쓰던 그 자리로 못박는다 | 다른 경로를 열면 앱은 멀쩡히 뜨고 화면만 빈다 |
| `@NSManaged` 145개 | 생성기가 뽑는다. 손으로 옮겨 적지 않는다 | 옮겨 적다 빠뜨리는 것이 이 일의 기본 사고다 |
| `awakeFromInsert` | `id` · `createdAt` 를 여기서 넣는다 | 모델의 기본값은 자리 채우기다 (`00000000-…`) |
| `@Query` 82곳 | `@FetchRequest` 로. 35곳은 인자 없고 47곳은 정렬 하나뿐이라 기계적이다 | |
| 심판 | CI 스크린샷 20여 장이 **이전과 같아야 한다** | 화면이 하나라도 달라 보이면 옮기다 흘린 것이 있다 |
| 되돌아갈 길 | 40번 백업·되돌리기 + 이전 TestFlight 빌드 | |


## 1b-1 — `@NSManaged` 선언을 뽑았다 (빌드에는 아직 안 넣음)

`Tools/coredata/generate-managed-classes.py` 가 **1a 와 같은 파서**를 써서
`App/Persistence/Generated/` 에 931줄을 뽑는다. 엔티티 15개 · 선언 148개.

`project.yml` 이 `Persistence/Generated/**` 를 제외하므로 **빌드에 안 들어간다.**
지금 넣으면 `@Model` 클래스와 이름이 겹쳐 깨진다. 이 단계의 일은 뽑아 놓고
**눈으로 보는 것**이고, 갈아타는 것은 1b-2 다.

### 눈으로 보는 것이 값했다

첫 판은 `awakeFromInsert` 를 프로퍼티 익스텐션에 넣고 있었다.
**Swift 는 익스텐션에서 메서드를 재정의할 수 없다.** 빌드에 들어가 있었다면
CI 한 바퀴를 썼을 것이다. 파일을 둘로 나눴다 —
`+CoreDataClass`(클래스 본문) · `+CoreDataProperties`(선언). Xcode 관례와 같다.

### 까다로운 곳 셋 — 어떻게 풀었나

| | 무엇이 문제인가 | 어떻게 |
|---|---|---|
| 옵셔널 스칼라 `Int?` (2개) | `@NSManaged` 가 값 타입 옵셔널을 못 든다 | `NSNumber?` 로 저장하고 `@objc(expectedReturnBP)` 로 KVC 이름만 맞춘 뒤, 쓰는 쪽 이름은 계산 프로퍼티로 되돌린다. **이미 있는 1,700줄이 안 바뀐다** |
| 일대다 (3개) | Core Data 는 `NSSet?` 이다. `[Account]?` 가 아니다 | 선언은 `NSSet?` 으로 두고, 정렬해 쓰는 곳(`sortedAccounts` 등 관계마다 한 곳)에서 푼다 |
| `id` · `createdAt` | 모델의 기본값이 자리 채우기다 (`00000000-…` · 2001-01-01) | `awakeFromInsert` 에서 진짜 값을 넣는다. 안 그러면 **모든 행의 id 가 같아진다** |

### 심판 하나를 더 세웠다

**빠진 `@NSManaged` 선언은 컴파일을 통과한다.** 그 값을 읽는 코드가 없을 뿐
빌드는 멀쩡하고, 화면에서 값 하나가 조용히 비는 것으로만 드러난다. 컴파일러가
못 잡는 자리다.

`check-managed-matches-model.py` 가 모델 파일의 칸과 생성물의 선언을 대조한다.
`@objc(x)` 가 붙은 것은 **KVC 이름 쪽**으로 견준다 — 모델이 아는 이름이 그것이다.
이것도 일부러 선언 하나를 지워서 확인했다:
`Member: 선언이 없는 칸 — colorIndex` · 종료코드 1.

### 1b-2 에 남은 것

| | |
|---|---|
| `@Model final class` 15개를 걷어내고 생성된 클래스로 바꾸기 | 계산 프로퍼티 1,700줄은 `extension` 으로 그대로 옮긴다 |
| `project.yml` 의 `excludes` 지우기 | 그 순간 생성물이 빌드에 들어간다 |
| `Persistence.swift` → `NSPersistentCloudKitContainer` | **저장소 경로를 SwiftData 가 쓰던 그 자리로 못박는다** |
| `@Query` 82곳 → `@FetchRequest` | 35곳은 인자 없고 47곳은 정렬 하나뿐이다 |
| `context.insert(x)` 등 생성 자리 | Core Data 는 `X(context:)` 로 만든다 |
| 심판 | CI 스크린샷 20여 장이 이전과 같아야 한다 |


## 1b-2 — 갈아탔다

`@Model` 15개가 사라지고 저장 계층이 `NSPersistentCloudKitContainer` 가 됐다.
**화면은 하나도 안 바뀌어야 한다** — 심판은 CI 스크린샷 20여 장이다.

| 무엇 | 어떻게 |
|---|---|
| `@Model final class X { 저장 프로퍼티 · init }` | 클래스는 생성물이 들고, 남은 계산 로직은 `extension X` 로. **저장 프로퍼티의 주석은 생성물이 데려갔다** |
| `init(...)` 15개 | `convenience init(context:...)`. Core Data 는 만드는 순간 컨텍스트에 들어가므로 `context.insert(...)` 50줄을 지웠다 |
| `@Query` 82곳 | `@Fetched` — 속은 `@FetchRequest`, 겉은 `[T]` |
| `@Bindable` 14곳 | 뷰 프로퍼티 8곳은 `@ObservedObject`, 지역 그림자 6곳은 `x.bindings` |
| `FetchDescriptor` 6곳 | `context.all(T.self, sortedBy:predicate:limit:)` |
| 일대다 3곳 | `NSSet?` 을 `sortedAccounts` 등 **한 곳씩에서만** 푼다 |
| `ModelContext` · `ModelContainer` | `NSManagedObjectContext` · `NSPersistentContainer` |

### `@Fetched` 를 왜 만들었나

`@FetchRequest` 를 직접 쓰면 타입이 `[Holding]` 에서 `FetchedResults<Holding>` 으로
바뀐다. 그러면 82곳이 아니라 **그 값을 넘겨받는 자리까지** 줄줄이 깨진다 —
`ReviewScheduling.Input(holdings:)` 처럼 `[Holding]` 을 받는 곳이 곳곳에 있고,
그건 CI 한 바퀴에 한 파일씩 발견하게 된다.

겉을 `[T]` 로 둔 덕에 82곳은 **이름 한 토큰만** 바뀌었다.

### 이 커밋에서 잃은 것 하나 — 그리고 되찾은 방법

**생성기가 더는 못 돈다.** `@Model` 을 읽어서 뽑는 도구였는데 그 `@Model` 이
사라졌기 때문이다. 실제로 무심코 한 번 돌렸다가 **생성물 서른 개를 전부
지웠다** — 지우는 것이 찾는 것보다 먼저였던 탓이다. 되살리고 빈손이면
아무것도 안 하도록 막아 두었다.

그래서 **원본을 옮겼다.**

```
App/SlowRich.xcdatamodeld          ← 원본
  ├─ App/Persistence/Generated/    ← @NSManaged 선언
  └─ Tools/cloudkit/slowrich.ckdb  ← CloudKit 스키마
```

칸을 더하면 셋을 함께 고친다. CI 는 이제 "다시 뽑아서 diff" 가 아니라
**셋을 서로 대조**한다(`check-model-matches-ckdb.py` ·
`check-managed-matches-model.py`). 파일만 읽으므로 생성기가 안 돌아도
잡아내고, 잡는 범위는 예전과 같다.

## 1b-2 에서 제일 값비쌌던 버그 — **조용히 틀린 숫자**

컴파일 오류 다섯 바퀴를 넘기고 앱이 뜬 뒤, 스크린샷을 대조했더니 22장 중
15장은 픽셀 단위로 같은데 **현황판·시뮬레이션·1페이지의 숫자가 달랐다.**
은퇴 예상이 63.1억에서 21.0억으로 떨어지고 `2082년에 바닥납니다` 가 새로 떴다.

### 원인 하나가 43곳에 퍼져 있었다

`.xcdatamodeld` 의 `defaultValueString` 은 **리터럴만** 담을 수 있다. 그런데
`@Model` 의 기본값 43개가 리터럴이 아니었다:

```swift
var startYear: Int = Calendar.current.component(.year, from: .now)
var kindRaw: String = AccountKind.general.rawValue
var id: UUID = UUID()
```

생성기는 이런 것을 **자리만 채워** 두었다 — `0` · `""` · `00000000-…`.
`UUID` 와 `Date` 는 `awakeFromInsert` 에서 진짜 값을 넣고 있었지만,
**연도 계산과 열거형 rawValue 는 빠져 있었다.** 그래서 `Plan.startYear` 가
0 이 되고 궤적이 통째로 어긋났다.

### 왜 무서운 종류인가

 · 컴파일된다
 · 앱이 뜬다
 · 화면도 멀쩡히 그려진다
 · **숫자만 틀리다**

타입 검사도, 빌드도, "앱이 살아 있나" 검사도 전부 통과한다. 스크린샷을
이전 것과 픽셀로 대조하지 않았으면 그대로 배포됐을 것이고, 사용자는
자기 은퇴 자금이 21억이라고 믿었을 것이다.

**이래서 심판이 스크린샷이다.** 1b-2 를 시작할 때 "화면이 하나라도 달라
보이면 옮기다 흘린 것이 있다" 고 적어 둔 것이 정확히 이 일을 잡았다.

### 고친 방법

`awakeFromInsert` 가 **리터럴이 아닌 기본값 43개를 전부** 넣는다. 생성기에도
같은 규칙을 넣어 두었다 — 원본(`Persistence.bak`)의 선언에서 그대로 읽어
쓰므로 손으로 옮겨 적은 값이 하나도 없다.


### 그리고 더 깊은 데 하나가 더 있었다 — **옵셔널에 기본값이 붙어 있었다**

기본값 43개를 채워 넣고 다시 찍었는데 **현황판 숫자가 그대로 틀려 있었다.**
`startYear` 는 원인이 아니었다는 뜻이다. 그래서 추측을 멈추고 계산 코드를 읽었다:

```swift
let key = Key(profile: profile,
              bp: account.expectedReturnBP ?? defaultReturnBP(for: profile))
```

`expectedReturnBP` 는 **옵셔널**이고, `nil` 은 "이 계좌만의 수익률을 안 정했다 —
계좌 종류의 기본값을 쓰라" 는 **뜻이 있는 값**이다. 그런데 모델 파일에는
`defaultValueString="0"` 이 붙어 있었다. Core Data 는 `nil` 대신 0 을 돌려주고,
`?? ` 가 한 번도 안 걸려서 **모든 덩어리가 연 0% 로 자랐다.**

같은 잘못이 다섯 곳에 있었다:

| | 무엇이 됐나 | 뜻이 무엇이었나 |
|---|---|---|
| `Account.expectedReturnBP` | 0 | 안 정했다 → 계좌 종류의 기본 수익률 |
| `Holding.targetWeightBP` | 0 | 목표 비중을 안 정했다 |
| `Account.ownerID` · `Holding.accountID` | `00000000-…` | 아직 안 이어졌다 |
| `UserMilestone.memberID` | `00000000-…` | **가족 전체의 일** |

내 생성기가 "필수 속성에는 기본값이 있어야 한다"(momc 규칙)를 옵셔널에까지
적용한 탓이다. 옵셔널 숫자는 `usesScalarValueType` 도 껐다 — `NSNumber?` 로
다뤄야 `nil` 이 살아 있다.

**검사를 하나 더 세웠다.** `check-model-matches-ckdb.py` 가 이제 "옵셔널인데
기본값이 붙어 있으면" 막는다. 일부러 붙여서 걸리는지 확인했다.

### 이 두 버그가 같은 얼굴을 하고 있다

기본값 43개도, 옵셔널의 기본값도, **컴파일되고 앱이 뜨고 화면도 그려지는데
숫자만 틀리는** 종류다. 저장 계층을 갈아탈 때 진짜 위험은 크래시가 아니라
이것이다 — 크래시는 눈에 띄지만 이건 안 띈다.

잡아낸 것은 **이전 스크린샷과의 픽셀 대조** 하나뿐이었다.

## 1c 에서 걸린 것 — **동기화만 안 붙었다**

기기에서 확인한 결과 1·2·4·5 는 되는데 3번만 안 됐다:

> 저장 방식 — **이 기기에만 저장**
> iCloud를 붙이지 못했습니다. 기록은 이 기기에만 있고…

### 먼저 이유를 볼 수 있게 만들었다

`Mode.localOnly(reason:)` 이 실패 이유를 **처음부터 들고 있었는데 화면에
안 내놓고 있었다.** 맥이 없어 디버거를 못 붙이는 이 저장소에서 유일한 길이
"화면에 띄우고 사용자가 읽어 주는 것" 인데, 그 길이 막혀 있었다.

추측으로 빌드를 태우지 않고 셋을 넣었다:

1. 이유를 동기화 화면에 그대로 (길게 눌러 복사됨)
2. `NSError` 를 펴서 `NSLocalizedFailureReason` 까지 —
   `String(describing:)` 은 정작 필요한 그 줄을 뭉갠다
3. **빈 저장소 탐침** — 실패한 뒤 임시 빈 파일로 한 번 더 열어 본다.
   그것도 실패하면 자격·모델 문제, 그것만 되면 쓰던 파일이 문제다

그 전에 무죄부터 가려냈다. 엔타이틀먼트는 빌드 24 IPA 에
`icloud-container-environment=Production` 까지 다 박혀 있었고, 모델도
유니크 제약 0 · 순서 있는 관계 0 · 관계 전부 옵셔널 · 타입은
Bool/Date/Int64/String/UUID 뿐이었다.

### 답 — **필수 UUID 열여섯 개**

```
NSCocoaErrorDomain 134060
CloudKit integration requires that all attributes be optional, or have a
default value set. The following attributes are marked non-optional but do
not have a default value:
  Account: id · CashEvent: id · … · SnapshotLine: memberID · (16개)

빈 저장소로도 iCloud 를 못 붙였습니다 — 파일 탓이 아닙니다: (같은 오류)
```

탐침이 "파일 탓이 아니다" 까지 한 번에 답했다.

**그런데 파일에는 열여섯 곳 모두 기본값이 적혀 있다:**

```xml
<attribute name="id" attributeType="UUID"
           defaultValueString="00000000-0000-0000-0000-000000000000"/>
```

**Core Data 는 UUID 속성에서 그 글자를 읽지 않는다.** Xcode 모델 편집기가
UUID 에 기본값 칸을 아예 안 내주는 것과 같은 이유다. 런타임의
`attribute.defaultValue` 는 `nil` 이고, CloudKit 은 그걸 본다.
`momc` 도 통과시킨다 — **파일에는 있고 런타임에는 없다.**

### 옵셔널로 돌리는 길은 못 쓴다

그게 첫 생각이었는데, **옵셔널 여부는 판본 해시에 들어간다.** 열여섯 곳을
옵셔널로 돌리면 해시가 달라지고 쓰던 저장소가 안 열린다 — 앱은 멀쩡히 뜨고
화면만 비는, 이 이전에서 제일 무서운 실패다.

**기본값은 해시에 안 들어간다.** 그래서 코드로 심는다
(`App/Persistence/ModelDefaults.swift`). SwiftData 가 이걸 어떻게 넘겼는지도
이제 설명이 된다 — 모델을 **코드로 만들어서** 심을 수 있었던 것이다.

### 심판을 세웠더니 한 시간 만에 값했다

파일 검사도 `momc` 도 못 잡는 종류라, **컴파일된 모델을 진짜 Core Data 로
열어** 묻는 검사기를 만들었다 (`Tools/coredata/check-cloudkit-model.swift`).
리눅스에서는 못 하는 일이라 macOS 러너에서만 돈다. 앱이 쓰는
`ModelDefaults` 를 **같이 컴파일해서 그대로 부른다** — 흉내 내면 둘이
어긋나는 날이 온다.

세운 지 한 시간도 안 돼서 첫 고침을 잡았다:

```
NSInternalInconsistencyException: 'Can't modify an immutable model.'
  -[NSAttributeDescription setDefaultValue:]
```

**컴파일된 `.momd` 에서 읽은 모델은 못 고친다.** 그대로 배포했으면 기기에서
앱이 뜨자마자 죽었다. `byMerging:` 으로 옮겨 담고 나서 심는다 — `copy()` 는
변경 불가 객체가 자기 자신을 돌려주는 흔한 최적화 때문에 안 쓴다.

검사기에 하나 더 물렸다: **옮겨 담은 뒤 판본 해시가 그대로인가.** 해시에
기본값이 안 들어간다는 것은 알지만, **그 믿음에 사용자의 기록을 걸지 않는다.**

### 남는 교훈

| 심판 | 잡는 것 | 못 잡는 것 |
|---|---|---|
| `check-model-matches-ckdb.py` | 세 파일이 서로 맞는지 | 파일에 적혀도 런타임이 안 읽는 것 |
| `momc` (컴파일) | 모델 문법 | 같음 |
| **`check-cloudkit-model.swift`** | **런타임이 실제로 보는 것** | 기기에서만 나는 것(자격·계정) |
| 기기 + 화면에 띄운 이유 | 나머지 전부 | — |

**아래로 갈수록 한 바퀴가 비싸다.** 그래서 위에서 잡을 수 있는 것을
아래로 흘려보내지 않는 것이 이 저장소의 규칙이고, 이번에 그 사다리에
한 칸이 비어 있었다.

```
저장 방식        iCloud 동기화
```

**1c 통과 — B-1(저장 계층 이전)이 끝났다.** 사용자 기록을 그대로 들고

# 2단계 — 공유 붙이기 (착수 전 실측)

## 재 보니 **매달린 것이 거의 없다**

`share(_:to:)` 는 넘긴 객체와 **관계로 이어진 것**을 공유 존으로 옮긴다.
그래서 공유에서 중요한 것은 칸 수가 아니라 **무엇이 무엇에 매달려 있나**다.
세어 봤다:

```
엔티티 15개 · 관계 3쌍
관계로 이어진 덩어리: 12개

   1. Account · Holding · Member
   2. Snapshot · SnapshotLine
   3. CashEvent      7. Plan          11. TodoItem
   4. ChangeLog      8. Principle     12. UserMilestone
   5. FamilyTarget   9. ReviewSession
   6. IncomeStream  10. Scenario
```

**열둘로 흩어져 있다.** 이 앱은 대부분을 관계가 아니라 UUID 칸
(`ownerID` · `accountID` · `memberID`)으로 잇는다 — CloudKit 제약 아래에서
관계를 최소로 두려던 선택이었는데, 공유에서는 그것이 그대로 값이 된다.

그리고 `Household` **엔티티는 없다.** 화면 제목은 `Plan.title` 이다
(CLAUDE.md 의 `Household.title` 은 오기다 — 이 커밋에서 고쳤다).

## 그래서 갈림길

| | 무엇 | 값 | 위험 |
|---|---|---|---|
| **A. `Household` 루트를 만들어 전부 매단다** | 엔티티 하나 추가 + 열다섯에 옵셔널 관계 하나씩 | 판본 해시가 **전부** 바뀐다 → 가벼운 이전 + CloudKit 스키마 재배포 | 이전은 자동으로 되는 종류(옵셔널 관계 추가). 다만 방금 지켜 낸 저장소를 한 번 더 건드린다 |
| **B. 루트 없이, 공유할 때 최상위 객체를 한꺼번에 넘긴다** | `share(열두 덩어리의 루트 전부, to:)` | 지금은 싸다 | **나중에 만든 것이 공유에 안 들어간다.** 새 계좌·새 점검이 아내분 화면에 조용히 안 보인다 |
| **C. 공유 범위를 좁힌다** | 구성원·계좌·종목만 | 작다 | 아내분 화면에 현황판·계획·궤적이 안 뜬다 — 요구를 못 채운다 |

**B 가 만드는 실패는 이 앱이 제일 경계하는 종류다** — 앱은 멀쩡히 돌고,
아내분 화면에서 값 하나가 조용히 빠진다. 그래서 권고는 **A** 다.

### A 로 갈 때 실제로 하는 일

1. `.xcdatamodeld` 에 `Household` 추가 + 열다섯 엔티티에 `household` 옵셔널 관계
2. 생성기 둘(`@NSManaged` · `ckdb`)을 다시 돌려 셋을 맞춘다
3. **CloudKit 스키마 재배포** — Actions → CloudKit 스키마 → 콘솔에서 Deploy
4. 앱이 뜰 때 `Household` 하나를 보장하고, 새로 만드는 객체에 물린다
5. `share([household], to: nil)` + `UICloudSharingController`
6. `.shared` 스코프 저장소를 하나 더 연다 (참가자 쪽이 쓰는 자리)
7. 참가자 권한을 `\.canEdit` 에 꽂고 `FamilyRole.swift` 를 지운다

**1~3 은 되돌리기 어렵다** (사용자의 실제 저장소와 Production 스키마).
그래서 여기서 한 번 멈추고 확인받는다.

## 2a 에서 드러난 것 — **저장이 없어져 있었다**

`Household` 를 매달 자리를 찾다가 저장 지점을 세었더니 앱 전체에 `.save()` 가
**세 곳**뿐이었고 셋 다 특수 경로였다(총액 빠른 입력 · 백업 복원 둘).

SwiftData 의 `ModelContext` 는 자동 저장이었다. 1b-2 에서 갈아타며 그것이
사라졌는데 **아무 데도 티가 나지 않았다.**

### 심판 넷이 나란히 못 잡았다

| 심판 | 왜 못 잡았나 |
|---|---|
| CI 스크린샷 | 인메모리 저장소라 **애초에 저장할 일이 없다** |
| 컴파일러 | 저장을 안 부르는 것은 오류가 아니다 |
| 런타임 모델 검사 | 저장 여부와 무관하다 |
| 1c 기기 확인 | **앱을 켠 채 한 바퀴** 돌아서 전부 정상으로 보였다 |

화면은 메모리에 있는 값을 그대로 보여 준다. 그래서 앱을 켜 둔 동안에는
저장이 되든 안 되든 **똑같이 보인다.**

### 남길 교훈 — **"없어진 것"은 스크린샷에 안 나온다**

1b-2 내내 심판은 "화면이 이전과 같은가" 였다. 그것은 **달라진 것**을 잡는
심판이지 **사라진 동작**을 잡는 심판이 아니다. 갈아타기에서 진짜 위험한 것은
후자다 — 자동 저장처럼 **원래 저절로 되던 일**은 없어져도 화면에 자국을
남기지 않는다.

그래서 1c 확인 목록의 **첫 줄을 "껐다 켜서 그대로인가"** 로 바꿨다.
갈아탈 때는 "무엇이 달라졌나" 만큼 **"무엇이 저절로 되고 있었나"** 를
세어야 한다.

### 고친 방법

`App/Persistence/Autosave.swift` 가 변경 알림을 듣고 400ms 모았다가 쓴다.
알림 안에서 바로 저장하면 재진입하므로 한 박자 미룬다. 앱이 내려갈 때는
`scenePhase` 가 `.active` 를 벗어나는 즉시 쓴다 — `.inactive` 에서 바로
끝낼 수 있어 `.background` 를 기다리지 않는다.

실패하면 더보기 → 동기화에 그대로 내놓는다. **조용히 삼키지 않는다.**

**빌드 27 에서 확인했다** (2026-09-08): 값을 고치고 앱을 완전히 종료한 뒤
다시 열어도 그대로다.

### 곁다리 하나 — 흔들리던 스크린샷의 진짜 원인

자동 저장을 넣자 `12-plan-keyboard` 가 또 `완료` 없이 찍혔다. 디바운스가
400ms 인데 `MoneyField` 의 CI 포커스 지연도 400ms 라 **둘이 같은 박자**였다.
저장이 컨텍스트를 흔들면 `@Fetched` 가 다시 읽고, 그 사이에 키보드 툴바가
포커스 변화를 놓친다. 1.2초로 넉넉히 물렸다.

앞서 "고쳤다" 고 적었던 것은 **한 번 잘 나온 것으로 판정한 성급함**이었다.
바닥 소음이 있는 심판에서는 한 표본으로 판정하면 안 된다는 것을 또 배웠다.

# 2b — 공유 붙이기 (**만들기 전에 합격 기준부터**)

이번 차수에서 두 번 당했다. 둘 다 **"확인했다고 생각했는데 확인한 것이
아니었던"** 경우다:

 · 1b-2 — 화면이 이전과 같아서 통과시켰는데, **저장이 없어져 있었다**
 · 1c — 기기에서 한 바퀴 돌아 통과시켰는데, **앱을 켠 채였다**

2b 는 그보다 더 어렵다. **두 사람·두 기기가 있어야 확인되는 첫 단계**이고,
아내분 기기에서 무엇이 안 보이는지는 이쪽에서 영영 안 보인다. 그래서 만들기
전에 **무엇을 보면 통과인지**를 먼저 적는다.

## 합격 기준 — 아내분 기기에서

| # | 확인할 것 | 왜 이것인가 |
|---|---|---|
| 1 | 초대 링크를 눌러 **앱이 열리고 참가된다** | 여기가 안 되면 나머지는 볼 것도 없다 |
| 2 | **현황판 숫자가 아빠 기기와 같다** | 공유 존으로 실제로 넘어갔는가 |
| 3 | 계획·궤적·1페이지가 **비어 있지 않다** | 열두 덩어리가 다 넘어갔는가 — `Household` 루트가 값하는 자리 |
| 4 | **보기 전용으로 보인다** — 편집·삭제·추가 버튼이 없다 | 참가자 권한이 `\.canEdit` 에 실제로 꽂혔는가 |
| 5 | **아빠가 새로 만든 계좌가 아내분 화면에 나타난다** | ⭐ 여기가 이번 설계의 핵심이다. 공유한 시점 이후에 만든 것이 따라오는지 — 루트 없이 갔다면 여기서 조용히 실패한다 |
| 6 | **앱을 껐다 켜도 그대로다** | 1c 에서 비어 있던 칸 |
| 7 | 권한을 넓히면 **본인 것만** 고쳐진다 | 4단계. 2b 에서는 아직 아니다 |

**5번이 이번 차수 전체의 시험이다.** 2단계 실측에서 덩어리가 열둘이라는 것을
보고 `Household` 루트를 만든 이유가 정확히 그것이고, 그 판단이 맞았는지는
5번으로만 알 수 있다.

## 아빠 기기에서

| # | 확인할 것 |
|---|---|
| 8 | 공유를 만든 뒤에도 **내 기록이 그대로다** — `share(_:to:)` 는 레코드를 다른 존으로 **옮긴다** |
| 9 | 더보기 → 동기화가 여전히 **성공**이다 |
| 10 | 공유를 **끊었을 때** 내 자료가 남아 있다 |

**8번과 10번을 미리 적어 두는 이유.** 공유는 자료를 private 존에서 **공유
존으로 옮기는** 일이다. 옮기다 잘못되면 그때 사라지는 것은 몇 달치 기록이다.
그래서 2b 를 올리기 전에 **백업을 받고**, 8번을 제일 먼저 본다.

## 만들 것

1. `.shared` 스코프 저장소를 하나 더 연다 — 참가자 쪽이 쓰는 자리
2. `share([household], to: nil)` + `UICloudSharingController`
3. 더보기에 "가족 초대" 자리
4. 참가자 권한을 읽어 `\.canEdit` · `\.canManageHousehold` 에 꽂는다
5. `FamilyRole.swift` 의 미리보기 장치와 더보기의 그 구역을 지운다

**5 는 4 가 확인된 뒤에 지운다.** 먼저 지우면 아내분 화면을 흉내 낼 방법이
사라져서, 공유가 안 붙는 동안 아무것도 못 본다.


## 2b 에서 막힌 것 — **링크를 생성할 수 없습니다**

초대 시트는 떴는데 사람을 더하려니 막혔다:

> 사람을 추가할 수 없음 — 공유를 위한 링크를 생성할 수 없습니다.

### 원인 — 시트를 여는 방식이 틀렸다

우리가 먼저 `share(_:to:)` 로 공유를 만들고
`UICloudSharingController(share:container:)` 로 넘기고 있었다. 그 초기화
함수는 **이미 서버에 저장된 공유**를 요구한다. 게다가 만든 **뒤에**
제목을 덧쓰고 저장하지 않아서, 서버본과 어긋난 것을 넘기고 있었다.
시트는 열리고 **참가자를 더하며 저장하는 순간** 막힌다 — 증상이 정확히
그랬다.

애플이 Core Data 용으로 문서화한 길은 `preparationHandler` 다. **UIKit 이
공유를 만들고 저장까지 맡는다.** 우리는 뿌리 객체를 넘기고 제목만 얹는다.
제목은 **넘기기 전에** 얹는다.

### 열어 둔 것 — 레코드 타입 권한

서버를 읽어 보니 16개 레코드 타입이 전부 이렇다:

```
GRANT READ, CREATE, WRITE TO "_creator"
```

`.ckdb` 를 3차에 쓸 때 "private database 전용이라 소유자만 읽고 쓴다" 고
정한 것이 그대로 남아 있다. 참가자는 `_creator` 가 아니다.

**그런데 이것을 원인으로 단정하지 않는다.** CloudKit 의 보안 역할
(`_creator` · `_world` · `_icloud`)은 주로 **공개 데이터베이스**에 적용되고,
private·shared 에서는 접근 권한을 `CKShare` 가 정한다. 확실하지 않은
이론으로 **되돌릴 수 없는 Production 스키마**를 또 건드리지 않는다.

**판정은 아내분 기기가 한다.** 초대가 붙은 뒤에도 화면이 비어 있으면
그때 이 권한을 의심한다. 그 순서를 지키는 것이 이 저장소의 방식이다.

## 2b 에서 막힌 것 ② — **`cloudkit.share` 가 Production 에 없었다**

앱이 안 죽게 된 뒤(아래 참고) "공유가 안 된 이유" 가 화면에 떴다:

```
Cannot create new type cloudkit.share in production schema
```

`CKShare` 는 `cloudkit.share` 라는 **시스템 레코드 타입**으로 저장된다.
CloudKit 은 그것을 Development 에서 앱이 처음 공유를 시도할 때 자동으로
만든다. 그런데 이 앱은 맥이 없어 Development 에서 돌아간 적이 한 번도 없다.
`CD_*` 타입에서 겪었던 함정(CLAUDE.md)을 시스템 타입에서 다시 겪은 것이다.

**이것이 처음부터 있던 진짜 벽이다.** 앞의 수정들은 각각 실제 버그였지만
이 벽 뒤에 가려져 있어서, 고쳐도 결과가 안 바뀌었다.

생성기가 `cloudkit.share` 를 함께 뽑아 같은 길(apply → Deploy)로 올린다.
서버는 시스템 필드만 받고도 `cloudkit.title` · `cloudkit.type` ·
`cloudkit.thumbnailImageData` 를 스스로 채워 돌려줬다. 이름에 점이 있어
따옴표가 필요하다 — 로컬 `validate` 는 통과시키고 서버 파서가 막았다.

### 그 앞에 있던 것 — **워치독**

크래시 로그가 알려 줬다:

```
FRONTBOARD 0x8BADF00D — exhausted real (wall clock) time allowance of 10.00 s
Thread 0 (main):
  -[_PFRequestExecutor wait]
  -[NSPersistentCloudKitContainer shareManagedObjects:toShare:completion:]
  -[UICloudSharingController __viewControllerWillBePresented:]
```

`share(_:to:)` 는 완료 블록을 받으면서도 **부른 스레드를 붙잡고 기다린다.**
`UICloudSharingController` 는 준비 핸들러를 메인에서 부르므로, 옮길
레코드가 수백 건이면 메인이 10초 넘게 멈추고 iOS 가 앱을 죽인다. 이제
백그라운드 컨텍스트에서 부르고 `objectID` 만 넘긴다.

### 이 자리에서 배운 것

**앱이 죽으면 API 를 고치기 전에 크래시 로그부터 읽는다.** 그 로그를 세
바퀴 늦게 요청했고, 그동안 증상만 보고 공유 API 사용법을 바꿔 가며
추측했다. 그중 둘은 고치면서 새로 심은 버그였다. 크래시 로그 한 장이
그 바퀴들을 한 번에 끝냈다 — 그리고 벽 뒤의 진짜 벽까지 보이게 했다.


# 4단계 — 참가자 권한을 `\.canEdit` 에 꽂았다 (2026-09-09, **검증 전**)

아내분 기기 시험을 기다리는 동안 미리 만들었다. 합격 기준 4번(보기 전용으로
보인다)과 3번(계획·궤적이 비어 있지 않다)은 이것 없이는 통과할 수 없었다.

## 역할은 `CKShare` 가 정한다

`FamilySharing.refreshState()` 가 **공유 저장소**에서 `fetchShares(in:)` 로
`CKShare` 를 찾는다. 있으면 참가자고, `currentUserParticipant.permission` 이
`readWrite` 면 `editor`, 아니면 `viewer` 다. 소유자의 공유는 개인 저장소에
있어서 여기 안 잡힌다 — 그래서 아빠 기기는 늘 `owner` 다.

판정한 역할은 `UserDefaults` 에 남긴다. 공유 조회는 백그라운드라 한 박자
늦는데, 그 사이 참가자 기기에 편집 버튼이 잠깐 보였다 사라지면 고장으로
읽힌다. 앱을 켜면 마지막 판정으로 먼저 뜨고, 곧 다시 읽는다. 앞으로 돌아올
때마다 읽으므로 관리자가 권한을 넓히면 다음에 앞으로 왔을 때 편집이 열린다.

`RootView` 는 참가자면 그 역할을 쓰고 미리보기 토글은 무시한다. 미리보기
띠도 안 띄운다 — 그 사람에게는 미리보기가 아니라 제 화면이다.
`FamilyRole.swift` 와 더보기의 미리보기 구역은 **아직 안 지웠다** (5번은
4번이 확인된 뒤). 참가자에게는 그 구역이 안 보인다.

## 참가자 기기의 가구는 하나로

초대를 받아들이는 순서가 문제였다. 링크를 누르면 앱이 먼저 뜨고, 첫 화면이
계획을 만들고, 저장이 그 계획을 새 가구에 매단다 — 공유 존이 내려오기
**전에**. 그래서 참가자 기기에는 늘 가구가 둘이 된다. `Plan` 도 둘이라
계획 화면이 어느 것을 보여 줄지 정해지지 않고, 빈 것이 걸리면 아내분
화면의 계획·궤적이 비어 보인다.

`Household.pruneEmptyLocalDuplicates` 가 치운다. 조건은 셋 다여야 한다:
공유 저장소에 **계획까지 내려온** 가구가 있고(참가자다), 이 가구는 개인
저장소에 있고, 계획 말고는 매달린 것이 하나도 없다. "계획까지" 인 이유:
공유 존은 레코드가 나눠 내려와서, 가구만 오고 계획이 아직이면 치운 직후
화면이 계획을 새로 만들어 공유 가구에 매단다 — 보기 전용의 쓰기는 서버가
거부하고 기기에는 계획이 둘 남는다. 관리자 기기에서는 첫 조건이 거짓이라
아무것도 안 한다. 참가자가 그 사이 무언가를 적었다면 세 번째 조건이 막는다.
관계 이름은 엔티티 정의에서 읽는다 — 열다섯 개를 손으로 적으면 하나
빠뜨리고, 그러면 그 종류의 기록이 든 가구를 빈 것으로 본다.

`Plan.current(in:)` 도 정렬 없는 `.first` 를 버리고 **가장 오래된 가구의
가장 오래된 계획**을 고른다.

## 아내분 기기에서 볼 것 (합격 기준에 더해)

| 확인할 것 | 어디서 |
|---|---|
| 더보기 → 가족 → `가족 공유: 참가 중 · 보기 전용` | 역할 판정이 됐는가 |
| 더보기 → 가족 → `상태` 가 `참가 중 · 보기 전용`, "가구가 2개" 경고가 **없다** | 빈 껍데기가 치워졌는가 |
| 편집·추가·삭제 버튼이 없고, 자리에 "보기 전용입니다" 가 있다 | `\.canEdit` 이 실제로 꽂혔는가 |
| 앱을 껐다 켜도 처음부터 보기 전용이다 | 판정이 저장되는가 |


## 2b 에서 막힌 것 ③ — **기존 기록이 뿌리에 안 매달려 있었다** (2026-09-10)

아내분 폰에서 초대를 받아들였다. `참가 중 · 보기 전용`, 동기화 `성공`,
가구 경고 없음 — 그런데 **기록이 하나도 안 보였다.** 합격 기준 3번이 그대로
잡아냈다.

### 원인

`Household` 는 4차 2a 에 생겼고, `Household.attachNew` 는 **저장할 때 새로
만든 것**만 뿌리에 매단다. 그 전에 만든 31종목·24주치·구성원·계좌·계획은
`household` 가 비어 있었다. 공유는 뿌리와 **관계로 이어진 것**만 옮기므로
아내분 폰에는 빈 가구만 갔다. 2단계에서 "덩어리가 열둘" 이라고 세고 뿌리를
만든 것까지는 맞았는데, **기존 기록을 그 뿌리에 매다는 한 번의 이전**을
빠뜨렸다. 새 기록만 매달리니 관리자 화면에서는 아무 티가 안 났다.

### 고친 것

`FamilySharing.adoptOrphans` — 소유자 기기에서 상태를 읽을 때마다
`household == nil` 인 기록을 전부 뿌리에 매단다. 엔티티는 모델에서
`household` 관계를 가진 것을 돌며 손으로 적지 않는다. 그리고 **공유가
이미 있으면 `share(_:to:)` 에 그 공유를 넘겨** 기록을 공유 존으로 옮긴다 —
관계만 이어서는 이미 개인 존에 올라간 레코드가 안 옮겨진다. 결과는 더보기 →
가족에 "기록 N건을 매달아 공유 존으로 옮겼습니다" 로 나온다.

### 교훈

**뿌리를 새로 만들 때는 "앞으로 만들 것" 과 "이미 있는 것" 을 따로 센다.**
`attachNew` 는 앞의 것만 맡았고, 뒤의 것은 아무도 안 맡았다. 두 기기가
있어야 보이는 실패라, 합격 기준을 먼저 적어 둔 것이 유일한 그물이었다.

### ③-2 — **옮기기는 `CD_moveReceipt` 에 막혔다**

44 로 매달기까지는 됐는데(98건), 공유 존으로 옮기는 단계가 통째로 거부됐다:

    Cannot create or modify field 'CD_moveReceipt' in record 'CD_ChangeLog'
    in production schema

레코드를 존 사이로 옮길 때 Core Data 가 붙이는 **이동 영수증** 필드다.
우리 스키마 파일은 모델에서 뽑아 내므로 이 시스템 필드가 없었고, Production
은 새 칸을 못 만든다. `cloudkit.share` 때와 같은 종류의 벽이다 — Development
에서 한 번이라도 옮겨 봤으면 자동으로 생겼을 칸.

고친 것: 생성기가 모든 `CD_` 타입에 `CD_moveReceipt BYTES` 와
`CD_moveReceipt_ckAsset ASSET` 을 넣는다. 검사기는 그것을 시스템 필드로
본다. 그리고 `adoptOrphans` 는 "매달렸는가" 가 아니라 **"공유 존에
있는가"** (`fetchShares(matching:)`) 를 보고 밖에 남은 것을 다시 옮긴다 —
매달림만 보면 첫 실패 뒤 영영 다시 안 옮긴다. 3분에 한 번만 시도한다.

같은 관리자 계정의 iPad 에서도 이 작업이 돈다. 두 기기 중 먼저 켠 쪽이 하고,
나머지는 옮겨진 것을 보고 아무것도 안 한다.
