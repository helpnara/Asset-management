# 14. 매일 점검 루틴 — 쓰는 화면 밖의 버그를 찾으려고

2026-09-29 에 시작했다. 사용자의 말 — *"내가 테스트하는 동안 사실 주간입력과
목실감만 쓰다 보니 추가 오류를 확인하기 어려운데 매일 체크해 보면 좋을 것들을
추천해 주면 어때?"* — 에 Claude 가 제안한 방식을 사용자가 받아들였다. **이
과정도 경험치이므로 근거를 남긴다** (사용자).

## 왜 필요한가

안정화 기준 3 · 4(자료 어긋남 없음 · 크래시 0, [로드맵](05-roadmap.md))는 **"4주 동안
아무 일도 없었다"** 로 채워진다. 그런데 매일 쓰는 화면이 주간 점검과 목·실·감 둘뿐이면,
나머지 화면에서는 버그가 있어도 **안 일어난 것처럼 보인다.** 기준은 차는데 제출 뒤
남이 처음 여는 화면에서 터진다.

실제로 그랬다. 189번(편집 화면에서 지우거나 새로 만들고 취소하면 죽음)은 계획 탭의
목돈 이벤트를 **평소에 안 지우다가** 188번 확인 중에 처음 눌러 드러났다. 그 크래시로
기준 4 의 시계가 10-17 에서 10-24 로 밀렸다. 한 번도 안 연 화면은 4주가 지나도 검사된 것이
아니다.

| 원칙 | 이유 |

| **지금까지 버그가 난 자리부터** | 삭제 · 취소(189), 두 기기 동기화(165 · 167), 계획선 숫자(162 · 188), 손잡이(163 · 166 · 169) |

| **실제 자료를 지우지 않는다** | 지우기 · 취소는 **테스트용으로 만든 항목**으로만. 기준 3 을 스스로 깨지 않게 |

## 발견하면

- **"어느 화면 → 무엇을 눌렀더니 → 무엇이 이상했다"** 한 줄. 스크린샷이 있으면 더 좋다.
- 앱이 죽으면 `설정 → 개인정보 보호 및 보안 → 분석 및 향상 → 분석 데이터` 의
  `SlowRich-…` 로그 ([12 교훈](12-lessons-learned.md) — 로그 없이 추측하지 않는다).
- 숫자가 기기마다 다르면 두 화면을 같이 찍는다.
- Claude 는 받은 것을 [08 피드백](08-feedback.md) 에 번호를 매겨 적고 로드맵 동결 표에
  올린다. 자료가 사라지거나 어긋나는 것만 바로 고치고, 나머지는 "착수하자" 때 묶는다.
